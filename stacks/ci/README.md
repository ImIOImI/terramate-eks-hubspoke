# `stacks/ci/` — local test environments for Argo and the hub/spoke wiring

**These stacks exist to test ArgoCD and its hub/spoke configuration, not to run
infrastructure.** They stand up a local copy of the real topology on
[MiniStack](https://ministack.org): no AWS account, no cost, and nothing here is
ever deployed by CI.

| Here (`stacks/ci/`) | Mirrors (`stacks/aws/`) | Role |
|---|---|---|
| `ci-hub` | `infra` | hub: runs ArgoCD |
| `ci-dev` | `dev` | spoke, registered with `ci-hub`; gets `k8s/kustomize/dev` |
| `ci-prd` | `prd` | spoke, registered with `ci-hub`; gets `k8s/kustomize/prd` |

```bash
make ci-apply   # all three envs (~18 min from cold), test the apps, print the hub ArgoCD URL + login
make ci-down    # remove everything
```

They are generated by the same bundle and components as the real stacks (never
edit them by hand). Only `stack_group: ci` in `_scaffold-cluster.tm.yml` puts them
in this folder; stack ids and ordering don't depend on it.

## What a green run proves

- Every stack applies in dependency order, with outputs-sharing between them
  (bootstrap → network → cluster → nodes → provisioning; spokes after the hub).
- Each spoke registers itself with the hub's ArgoCD (a cluster secret written
  into the hub), and the hub can reach and authenticate to both spokes.
- The hub's ArgoCD manages its own apps from git (`k8s/argo`, app-of-apps) and fans
  them out to both spokes through ApplicationSets: the Argo Rollouts controller,
  plus the `k8s/kustomize` hello apps, each spoke on its own overlay.
- Every Application gets to **Synced + Healthy**, and Argo Rollouts canaries
  progress (50% → pause → 100%).

## Why the auth is different here

Real spokes register with ArgoCD using **`awsAuthConfig`**: the hub's ArgoCD
controller assumes the spoke's `tmhs-argocd-spoke-access` IAM role and gets an
**EKS token** for the spoke cluster's endpoint. MiniStack can't do that path:

1. **No EKS token auth.** MiniStack's EKS creates a real k3s cluster, but there is
   no aws-iam-authenticator in front of it, so any EKS token gets a `401`. The only
   way in is k3s's own admin **client certificate**, so locally:
   - tofu's kubernetes/helm providers use that cert (read from `.ministack/`), and
   - each spoke registers with ArgoCD using `tlsClientConfig` (cert + key + CA)
     instead of `awsAuthConfig`.
2. **No usable endpoint.** MiniStack reports each cluster as
   `https://localhost:<port>`, which only works from your laptop, not from inside
   the hub's ArgoCD pod. Local spokes register with their k3s container's
   **Docker bridge IP** instead (k3s's serving certificate includes that IP).
3. **No role assumption.** MiniStack authenticates purely on the access key (which
   it turns into the account id), so there are no `assume_role` blocks. The
   spoke-access IAM role is still created, but nothing assumes it locally.

The local variants are separate `generate_hcl` blocks in the components, so the
real stacks' generated code is byte-identical with or without them.

**So a green run here does NOT prove** EKS token auth or the hub controller's
cross-account role assumption into the spokes. Those only run against real AWS.
Everything else, from the stack graph to the ArgoCD sync, is exercised against
real Kubernetes API servers.

Full details, including the smaller MiniStack gaps (IRSA, AMI lookup, pod identity), are in
[MINISTACK.md](../../MINISTACK.md).
